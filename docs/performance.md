# Measuring MCP performance

Run the maintained synthetic workload without ERP access:

```sh
npm run benchmark:mcp -- --mode=offline --output=artifacts/performance/offline.json
```

The script builds the current source, uses explicit synthetic configuration and fixture-origin-only fetch responses, and runs process tests with the network-blocking preload. It never reads `.env` or real credentials. Only `offline` mode exists. The fixture is versioned at `tests/fixtures/performance/workloads.json`.

Nine workloads include full and operations manifests. Each workload records 50 samples, latency min/p50/p95/max/mean, serialized JSON payload bytes, backend-call counts, transport/process mode and cache state. The artifact records the revision, dirty flag, timestamp, Node, OS, architecture and CPU. Imports and OS disk caches are warm; a fresh child process is a process-cold measurement, not a guarantee of cold filesystem caches. Startup measurements include initialization, discovery and shutdown. The catalog workload counts all pages and their combined response bytes; returned summary JSON bytes are reported separately. The warm lookup uses a prepopulated response cache. The burst fixture sends 20 identical concurrent reads. Search asserts the match on row 250 despite a 100-row server page cap. The formatter starts with at least 1MiB of synthetic data. A small signed-amount golden fixture checks that result formatting preserves its total; it does not validate tenant accounting semantics.

`docs/audits/2026-10-25/performance/baseline.json` is a one-time historical planning reproduction. Keep it separate from maintained runs. Compare only artifacts with matching fixture versions, hardware, Node, transport and cache state. The benchmark raises its synthetic rate allowance to avoid measuring a minute-long local quota pause. Live configured quotas, retries and ERP latency require separate controlled measurements.

Local acceptance targets are warm cached lookup p95 under 50ms and 1MiB formatter p95 under 30ms. A passing synthetic result does not establish a live improvement. Host/model turn latency, tool-choice accuracy, wire duplication actually included in model context, token usage and interactive/report live p95 require a separately recorded host replay with pinned host/model versions, approved read-only scenarios, complete evidence and comparable cache state. JSON bytes are not tokens. After all deterministic gates pass, the completion label is **offline-complete / live-performance-unverified** until that replay exists.

## Runtime aggregates and privacy

`PriorityClient.metrics` owns one `MetricsCollector`. `recordMetric(event)` and `metricsSnapshot()` use only the current operation's collector; with no collector they drop the event or return an empty snapshot. `withOperation`, `currentOperation` and `createOperation` use AsyncLocalStorage, preserving isolation across concurrent and nested calls. The registry creates opaque trace IDs and propagates MCP cancellation. Context creation starts no timer or ERP I/O. Deadlines default to 20 seconds for interactive/verification and 120 seconds for report/discovery work; enforcement belongs to request scheduling.

Tool, queue, network-attempt (including body read), retry sleep, cache, JSON parsing and result normalization/serialization boundaries emit aggregate metrics. Network bucket counts are backend attempts, not successful business operations. Histogram buckets are noncumulative <=1, <=5, <=20, <=100, <=500, <=2000 and >2000 milliseconds. Durations/bytes/counter values are finite nonnegative numbers. `count` is event count; `value` sums numeric row/page amounts and never carries business amounts. No individual request list is retained. Registry serialization measures normalization plus an extra serialization needed to account payload bytes; it is not transport flush time.

Labels contain static catalog tool/form names and finite method/phase/outcome/cache enums. Unknown forms become opaque SHA-256 label prefixes. Each collector retains at most 256 form labels plus `overflow`, and at most 2048 aggregate series plus a single overflow series. Overflow discards label attribution but preserves event totals. No URLs, query parameters, names, record keys, credentials, response contents or raw errors enter metrics. Client debug logs contain method, attempt, status and opaque trace ID; retry warnings omit errors and payloads. Logger output remains on stderr and redacts raw URL/query/filter/body/error fields as defense in depth.

`priority_healthcheck({diagnostics:true})` exposes a snapshot from **only the PriorityClient bound to that server**. Diagnostics are absent by default. Calling it does not probe the backend unless `checkBackend:true` is also requested. HTTP sessions intentionally sharing that client see its combined local aggregates; distinct clients, even constructed with the same configuration object, do not share diagnostics. This client boundary follows existing authenticated backend pooling. Diagnostics contain no scope fingerprint and grant no backend permissions. The currently executing healthcheck's final timing appears only on a later snapshot. Normal tool-result bounds may trim a very large diagnostics snapshot; use collector access in an offline harness for complete local exports.
