# פורטל בקשות מקומי — דמה ל־Instinct

האתר נוסף ב־`src/web/` ומשתמש ב־TypeScript, Hono, Zod ו־Vitest שכבר מותקנים ובמנגנון חסימת הכתיבה הקיים.
אין בו קליינט Priority/MCP, בוט Telegram, webhook או polling. נקודת הכניסה הקיימת `src/index.ts` לא שונתה.
אין פריסה ציבורית ואין כתיבה לייצור.

## מה עובד

- טופס התחברות רגיל עם `autocomplete=username/current-password`, עבור כספת הדפדפן. אין העברת סודות בצ׳אט.
- ממשק עברי RTL ללא JavaScript, CDN או שירותי צד שלישי; labels וטפסי submit רגילים.
- בקשה לחשבונית מס־קבלה, ספק חדש, הזמנת רכש לספק דמה ובקשה משולבת לספק חדש ולהזמנה.
- רשימות לקוחות/מוצרים/ספקים מדומות. גם הפרטים שהמשתמש מקליד חייבים להיות נתוני דמה.
- רשימת בקשות של המשתמש, חיפוש לפי אסמכתה מדויקת, עימוד, תוצאה ויומן פעולות לכל בקשה.
- SQLite מקומי: בקשה ותוצאה באותה טרנזקציה, UUID קבוע, גרסה 1 נעולה ו־SHA-256 של תוכן קנוני הכולל יוצר, גרסה ויעד `demo-only`.
- מניעת כפילות לפי `(actor_id, submission_key)` וגם `(actor_id, reference)` עם UNIQUE ו־`BEGIN IMMEDIATE`.
  שליחה חוזרת של אותו תוכן מחזירה אותו מזהה; אסמכתה/מפתח ששימשו לתוכן שונה מחזירים 409.
  גם מפתחות חדשים של שליחות חוזרות נקשרים לצמיתות לבקשה בטבלת `submission_keys`; אי אפשר למחזרם לתוכן אחר.
- יומן מקומי מצטבר: כניסה, כישלונות, הגבלת ניסיונות, שליחה, כפילות, קריאה וחסימות אישור/ביצוע.
- חשבון `agent` בלבד, סיסמת scrypt עם salt אקראי, session אקראי שמור בשרת כ־hash, תפוגת 8 שעות וביטול ביציאה/החלפת סיסמה.
- CSRF גם בהתחברות, בדיקת Origin/Host, HttpOnly/SameSite=Strict, CSP ללא סקריפטים, escaping, מגבלת גוף 16KB והגבלת כניסות במסד.
- POST ישיר ל־`/requests/:id/approve` או `execute` נחסם בשרת גם עם session ו־CSRF תקפים ופרמטרים שמתחזים לבעל החשבון.
  שינוי `PRIORITY_READ_ONLY`, `confirm` או `dryRun` אינו מפעיל כתיבה מהאתר.

התוצאה מציינת רק **נשמר באתר**, עם `priorityVerified=false` ורשימת רשומות ריקה. אין מספר מסמך מדומה,
הצלחה חשבונאית או טענה שנשלח אישור. טפסי החשבונית/הרכש כוללים פריט אחד, ILS ומחיר לדוגמה;
חישובי מס, תשלום בפועל, הפקה וסגירה אינם ממומשים.

## הפעלה

מתוך `priority-mcp-server`, עם Node 22.13 ומעלה:

```bash
npm ci
npm run web:setup
npm run web:start
```

`web:setup` מבצע build ושואל במסוף על שם משתמש וסיסמת **האתר** (16–128 תווים, מוסתרת בזמן ההקלדה).
אפשר להריץ שוב להחלפת סיסמה וביטול sessions ישנים. אין להזין סיסמת Priority.
חלופה להתקנה ראשונה, ללא הצגת הסיסמה במסוף או בצ׳אט:

```bash
npm run web:setup -- --generate
```

נוצרים חשבון `instinct` וסיסמה אקראית בקובץ `.local-web/agent-login.txt` בהרשאות 0600.
ייבאו אותה לכספת באופן מקומי ומחקו את הקובץ לאחר הייבוא. במסד נשמר רק hash.
הפקה חוזרת מסרבת לדרוס חשבון/קובץ קיימים. התיקייה מוחרגת מ־git ומ־Docker ואינה מוגשת באתר.

כתובת: **http://127.0.0.1:3210/login**. `localhost` אינו ה־Host המותר בגרסה זו.
המסד הוא `.local-web/requests.sqlite` וקובצי WAL נלווים. עצירה: Ctrl+C.
אחרי עריכת קוד: `npm run build` ואז `npm run web:start`.

| משתנה | ברירת מחדל | הערה |
| --- | --- | --- |
| `WEB_PORT` | `3210` | 1024–65535; לשנות גם ב־setup וגם בהפעלה |
| `WEB_DB_PATH` | `.local-web/requests.sqlite` | אותו נתיב ב־setup ובהפעלה |
| `WEB_HOST` | `127.0.0.1` | כל ערך אחר נחסם |
| `WEB_MODE` | `demo` | כל ערך אחר נחסם |

השרת לא טוען `.env` של Priority ולא צריך שרת MCP לצורך פעילות האתר.
ה־cookie המקומי אינו Secure משום שהשרת הוא HTTP מקומי בלבד. אירוח פרטי עתידי מחייב TLS,
Secure cookies, כתובת מורשית ו־proxy מוגדר — שינוי ופריסה נפרדים.
אם דפדפן Instinct פועל במכונה מרוחקת, loopback אינו נגיש לו. נדרשת הרצה לצד הדפדפן או קישוריות פרטית
מאושרת בהמשך; לא נוצר tunnel ולא נפתחה גישה ציבורית.

## בדיקת קבלה בדפדפן

1. ייבאו את פרטי האתר לכספת מקומית. פתחו `/login` והיכנסו דרך הטופס.
2. בחרו חשבונית מס־קבלה. הזינו `DEMO-INVOICE-001`, לקוח/מוצר לדוגמה, תאריך תקין,
   כמות 2, מחיר 12.35, אמצעי תשלום ואסמכתת תשלום פיקטיבית. סמנו נתוני דמה ושלחו.
3. ודאו שמוצגים UUID, גרסה 1, התוכן והתוצאה ״לא נוצרו רשומות ב־Priority״. הסכום 24.70 הוא הדגמה ללא חישוב מס.
4. חפשו את האסמכתה ב״הבקשות שלי״ ופתחו מחדש את התוצאה.
5. שלחו שוב אותה אסמכתה ואותו תוכן: חייב לחזור אותו מזהה. תוכן שונה באותה אסמכתה ייחסם.
6. נסו ספק ורכש, כולל ״ספק חדש + הזמנת רכש״, עם מספר עוסק `000000000` ודוא״ל `demo@example.test`.
7. בצעו יציאה ופתחו כתובת בקשה ישירות: יש להפנות להתחברות.

```bash
npm test
npm run build
npm run test:mcp
./node_modules/.bin/biome check src/web tests/web scripts/smoke.mjs scripts/offline-network.mjs
```

`tests/web/portal.test.ts` בודק זרימות HTTP/טפסים, הרשאות, CSRF, XSS, מגבלות, כפילויות מקבילות,
פתיחת SQLite מחדש ושתי התקשרויות למסד. כל ניסיון fetch חיצוני מכשיל את בדיקות האתר.
`test:mcp` בודק את השרת הבנוי בפרוטוקול MCP stdio עם תצורה פיקטיבית וחסימת fetch בתהליך הבן.
הוא מאמת רישום כלים, dry-run וחסימות כתיבה ונכשל כשחסר כלי/הגנה; אין בדיקה מול חברה אמיתית.

[תוצאות הבדיקות שבוצעו, כולל דפדפן אמיתי](web-verification.md).

## בדיקת הקוד הקיים

המיפוי מבוסס על המקור המקומי. הערות ישנות על אימות בחברה מסוימת אינן אימות חדש ואינן מוכיחות התאמה לחברת הבדיקות העתידית.

| תחום | קוד קיים | משמעות |
| --- | --- | --- |
| חיבור Priority | `client/priority-client.ts`, `client/auth.ts`, `config.ts`: OData, PAT/Basic וכותרות רישוי | לשימוש חוזר בשרת בלבד; לא להעביר פרטי חברה, credentials או כתובות חיבור לדפדפן |
| כלי MCP | `server.ts`, `tools/index.ts`, `tools/*`: רישום עם allow/block lists | כלים חסומים אינם ניתנים לקריאה; האתר אינו חושף כלי MCP |
| הגנות כתיבה | `lib/write-guard.ts`, `PriorityClient.send` | read-only כברירת מחדל ובדיקת הגנה גם בשכבת HTTP; האתר משתמש ב־guard עם read-only קשיח |
| הרשאות HTTP | `index.ts`, `lib/http-auth.ts`: loopback, Bearer token ו־Origin allowlist | מיועד לקליינטי MCP; לא מתאים לכספת שממלאת טופס בלבד, ולכן הוסף session נפרד לאתר |
| חשבונית | `priority_create_invoice` ב־`tools/invoices.ts`, יצירה ב־`AINVOICES` עם שורות | קיימת יצירת חשבונית בקוד; **אין תהליך ייעודי מאומת לחשבונית מס־קבלה**, תשלום, התאמה והפקה |
| ספק | `tools/suppliers.ts`: list/search/get; balance עשוי להחזיר unavailable | **אין כלי ייעודי ליצירת ספק**; API גנרי אינו תהליך עסקי מאומת |
| הזמנת רכש | `priority_create_purchase_order` ב־`tools/purchase-orders.ts`, `PORDERS` ושורות | קיים מימוש ו־dry-run; דרושים אימות metadata בחברת הבדיקות, read-back ושמירת מזהה מאומת |
| כתיבות נוספות | generic create/update/add-line; לקוחות; מכר; חשבוניות/זיכויים; נספחים; תיקי יבוא וקישורים | אינן נחשפות באתר. חלק מהכלים מחזירים unavailable; רישום כלי אינו הוכחת תמיכה |
| retry | `isRetryable` ב־`priority-client.ts`: כתיבות אינן חוזרות אחרי רשת/5xx, יש חריגת 429 | worker עתידי חייב reconciliation; לבחון גם 429 בפעולה כספית |
| Telegram | לא נמצאו בוט, webhook, polling, ספריית Telegram או מנגנון אישור בסביבת העבודה | **לא נבנה בוט ולא שונה בוט קיים**; איתור וחיבור למימוש חיצוני הם פער עתידי |
| פריסה | package scripts, stdio/HTTP, GitHub Actions ל־lint/test/build/Docker, `docs/deployment.md` | Docker/Cloud Run/Railway מוזכרים בתיעוד, אך **אין Dockerfile במאגר המקומי**; לא אומתה פריסה פעילה ולא הופעלו פקודות פריסה |

הנתיבים בטבלה יחסיים ל־`src/` אלא אם נאמר אחרת. השינויים המקומיים שהיו בתחילת העבודה נשמרו ונכללו
ב־build ובבדיקות. תהליך MCP שכבר רץ עשוי להזדקק לטעינה מחדש כדי לקרוא את `dist` המעודכן;
לא שונו הגדרות MCP במחשב ולא הופעל מחדש שירות שעלול לשמש את הבוט.

## אישור וביצוע עתידי — תכנון בלבד, ללא בניית בוט

`src/web/policy.ts` הוא חוזה מדיניות טהור עם בדיקות. הוא **אינו מאמת Telegram**, אינו שומר אישורים
ואינו מפעיל worker. `authenticatedOwner` חייב בעתיד להיקבע בשרת אחרי אימות חיצוני, לעולם לא מגוף בקשת דפדפן.
ב־V1 אין דרך לאשר בכלל; כל תוכן שנשלח נעול לשינוי.

1. snapshot נשמר עם UUID, יוצר, גרסה, target company מאומתת ו־hash. שינוי עתידי יוצר גרסה חדשה
   ומבטל את כל האתגרים/האישורים הקודמים. האישור קשור גם למיפוי הפעולה הסופי ולסכומים שיוצגו לבעל החשבון.
2. חיבור נפרד לבוט הקיים מציג לבעל החשבון את התוכן המדויק, הגרסה, ה־hash, החברה ותוקף של עד 10 דקות.
   יש לאמת את ערוץ העדכון, מזהה המשתמש הקבוע, chat פרטי ו־message ID המקושר לאתגר.
   username, הודעה מועברת או `owner=true` אינם ראיה. אין להקים webhook/polling מתחרים לבוט הקיים.
3. callback אטום ואקראי יקושר ברשומת שרת לכל פרטי האישור. token נשמר כ־hash ונצרך פעם אחת בטרנזקציה.
   הסוכן אינו יכול להנפיק או לאשר את האתגר.
4. worker נפרד מאמת שוב בעל חשבון, הפרדת תפקידים, תוכן/גרסה/יעד, תפוגה ואי־שימוש קודם.
   צריכת אישור ותביעת job אטומיות; attempt נשמר לפני dispatch. כפתור אינו הרשאה.
5. שימוש ב־PriorityClient ובפעולות הקיימות רק לאחר אימות סכמות ותהליכים בחברת הבדיקות.
   אין API/SQL/shell גנרי או בחירת endpoints לסוכן.
6. כל צעד נשמר בנפרד (ספק, הזמנה וכו׳). `created_records` מיועדת לסוג, מזהה וזמן אימות לאחר read-back
   מול Priority. הטבלאות `execution_attempts` ו־`created_records` הוכנו אך אינן מאוכלסות ב־V1.
7. timeout, ניתוק, 5xx או קריסה לאחר dispatch → מצב `uncertain`; גם attempt שנותר `in_progress`
   מחייב reconciliation. היעדר תגובה אינו הוכחה שהרשומה לא נוצרה.
8. reconciliation משתמש במזהה חיצוני ייחודי **שיש לאמת שניתן לכתוב ולחפש ב־Priority**, ללא cache,
   ובודק חברה, תוכן, מפתחות מלאים ומסמכי המשך. נמצא מסמך תואם אחד → שמירת מזהה מאומת;
   כמה התאמות/אי־ודאות → בדיקה ידנית; הוכח שלא נוצר → אפשר לשקול ניסיון חדש, עם אישור חדש לפי הצורך.
   אין retry עיוור ואין יצירת ספק כפול כשממשיכים הזמנה שנכשלה חלקית.

אחרי ניתוק בזמן שמירה **באתר**, יש לחפש את האסמכתה או לשלוח שוב אותו תוכן באותה אסמכתה.
הטרנזקציה ואילוץ UNIQUE מחזירים את התוצאה הקיימת. אסמכתאות שונות הן בקשות עסקיות שונות;
אין מניעת כפילות סמנטית בין אסמכתאות שונות. יומן SQLite אינו ביקורת חיצונית עמידה בפני בעל הרשאות DB/מערכת.

## פערים לקראת חברת בדיקות

- חברת בדיקות מוגדרת ומאומתת שאינה ייצור, חשבון Priority מוגבל וסודות בצד השרת בלבד.
- גילוי forms/metadata, שדות חובה, סוגי מסמכים, סטטוסים ומפתחות בפועל — אין להסיק שמות לפי השערה.
- מימוש מאומת של חשבונית מס־קבלה, תשלום, מסים, התאמה, הפקה וסגירה בהתאם להתקנה.
- מימוש יצירת ספק, בדיקת כפילות וזיהוי יצירה חלקית; אין כרגע כלי ספק ייעודי לשימוש חוזר.
- אימות `priority_create_purchase_order`, יחידות, מטבע/מחיר/מס ומפתחות בחברת הבדיקות.
- חיבור מאומת לבוט הקיים, persistence לאתגרים/אישורים, ביטול, תפוגה וצריכה אטומית; ללא שינוי התנהגות הבוט.
- worker עם נעילות/leases, ledger, מזהים מאומתים ו־reconciliation ייעודי לכל פעולה.
- correlation אמין בצד Priority. אם אין חיפוש אמין, אי־ודאות מחייבת טיפול ידני ולא retry.
- בדיקה בדפדפן Instinct עם הכספת שלו וקישוריות פרטית; בדיקות דפדפן מקומיות אינן הוכחה לאינטגרציה הזו.
- לפני אירוח משותף: TLS, Secure cookies, Host/Origin/proxy, גיבויים מוצפנים, retention ומעקב שאינו חושף סודות.

מקורות התשתית: [Node SQLite](https://nodejs.org/api/sqlite.html) (ללא דגל מ־22.13),
[Hono](https://hono.dev/docs/api/hono), [Telegram Bot API](https://core.telegram.org/bots/api#callbackquery)
לתכנון העתידי בלבד. מקורות אלה לא שימשו לניחוש סכמת Priority.
